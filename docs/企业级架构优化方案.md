# Api-Web 企业级架构优化方案

> 版本：v1.0　日期：2026-10-11　状态：待评审
> 目标：将现有单体架构补齐为符合大厂企业级标准的分层、可观测、可演进、可回归的工程体系。

---

## 一、现状评估结论

### 1.1 已具备的企业级基础（保留，不推翻）

| 能力 | 实现 | 评价 |
|---|---|---|
| 统一响应格式 | `Result<T>` + `ErrorCode` 业务码体系 | ✅ 规范 |
| 全局异常处理 | `GlobalExceptionHandler`（业务/校验/参数绑定全覆盖） | ✅ 规范 |
| 认证与鉴权 | JWT 无状态 + `@RequireRole` 角色切面 + `UserContext` | ✅ 规范 |
| 密码与密钥安全 | BCrypt 密码 + AES-GCM 密钥加密（`AesGcm`） | ✅ 规范 |
| 配置外部化 | DB/Redis/MQ/MinIO/JWT/安全白名单 全部环境变量注入 | ✅ 规范 |
| 消息队列抽象 | 交换机/队列/路由键全部可配置 + 消费端条件开关 | ✅ 规范 |
| 定时任务 | Quartz 集群（JDBC 存储 + 行锁防重复触发） | ✅ 规范 |
| 审计日志 | `@AuditLog` AOP 自动落库（含变更前后值） | ✅ 规范 |
| 执行引擎 | `StepExecutor` 策略模式 + `StepExecutorRegistry` 注册表 | ✅ 设计优秀 |
| 对象存储 | 超 1MB 请求/响应体转存 MinIO，DB 只存引用 | ✅ 合理 |
| 幂等迁移 | `migrate.sql` 手工幂等脚本 | ⚠️ 需升级为版本化 |

### 1.2 不符合企业级的关键差距

| # | 差距 | 严重度 | 现状证据 |
|---|---|---|---|
| G1 | **Controller 直接注入 Mapper，Service 层缺失** | 🔴 高 | 19 个 Controller 全部直接注入 `*Mapper`，无业务 Service 隔离 |
| G2 | **无 DTO/VO 分层，Entity 直接出入参** | 🔴 高 | `Result<CaseEntity>` 等，表结构变更直接冲击 API 契约 |
| G3 | **无 API 文档** | 🟡 中 | pom 无 springdoc/openapi 依赖 |
| G4 | **无可观测性（监控/健康检查/指标）** | 🟡 中 | pom 无 actuator/micrometer/prometheus |
| G5 | **测试覆盖严重不足** | 🔴 高 | 后端仅 8 个单测（枚举/工具类），前端 0 测试 |
| G6 | **数据库无版本化迁移** | 🟡 中 | 依赖手工 `migrate.sql`，无 Flyway/Liquibase |
| G7 | **前端无工程规范** | 🟡 中 | 无 ESLint/Prettier，无单测框架 |
| G8 | **缺少统一分页/错误码/DTO 基础组件** | 🟢 低 | 分页各自为战，DTO 散落 `EngineDtos` |

## 二、优化目标与原则

### 2.1 目标

1. **分层清晰**：Controller → Service → Mapper 严格单向依赖，业务逻辑收敛到 Service，事务边界明确。
2. **契约稳定**：API 出入参用 DTO/VO，与表结构解耦，可独立演进。
3. **可观测**：健康检查、指标、链路日志、API 文档开箱即用。
4. **可演进**：数据库变更版本化、可回溯、可回滚。
5. **可回归**：关键链路有自动化测试兜底，改动不破坏既有功能。

### 2.2 原则

- **渐进式、不推翻**：保留已验证的 engine / security / config / mq 设计，只补短板。
- **小步提交、随时可编译**：每完成一个模块立即编译验证 + 单测 + commit。
- **兼容优先**：重构期间保持 API 契约不变（字段名、路径、错误码），前端零改动。
- **风险隔离**：高风险项（G1/G2）单独成阶段，先建基线测试再重构。

## 三、分阶段实施计划

> 按「风险从低到高、收益从高到低」排序。每个阶段独立可交付、独立可回滚。

### 阶段 0：工程基建（低风险，先做）
**目标**：搭好可观测性 + 测试骨架，为后续重构提供安全网。

| 项 | 内容 | 影响面 |
|---|---|---|
| P0-1 | 引入 `spring-boot-starter-actuator` + `micrometer-registry-prometheus`，暴露 `/actuator/health`、`/actuator/metrics`、`/actuator/prometheus` | 新增依赖 + 配置，无业务侵入 |
| P0-2 | 引入 `springdoc-openapi-starter-webmvc-ui`，生成 `/v3/api-docs` + `/swagger-ui.html`，并纳入认证白名单 | 新增依赖 + 配置 |
| P0-3 | 引入 Flyway，`db/migration/V1__baseline.sql`（含现有 31 表 + 幂等迁移合并），baseline-on-migrate 兼容老库 | 替代 migrate.sql，需一次性整理 |
| P0-4 | 前端接入 ESLint + Prettier + Vitest + @vue/test-utils | 新增配置文件，不强制全量整改 |
| P0-5 | 统一分页响应 `PageResult<T>` + 分页工具类 | 新增基础组件 |

**验收**：后端 `/actuator/health` 返回 UP，`/v3/api-docs` 可访问，Flyway 迁移在新库/老库均通过；前端 `npm run lint`、`npm run test` 可运行。

---

### 阶段 1：DTO/VO 分层（中风险，收益高）
**目标**：API 出入参从 Entity 迁移到 DTO/VO，切断表结构与 API 契约的耦合。

| 项 | 内容 |
|---|---|
| P1-1 | 新建 `dto/`、`vo/` 包，制定命名规范（`XxxCreateReq` / `XxxUpdateReq` / `XxxQuery` / `XxxVO`） |
| P1-2 | 按域逐个迁移：user → project → environment → globalVariable → module → case → apiDefinition → scenario → task → report → ui → perf → ci |
| P1-3 | 引入 MapStruct（或手写 `BeanUtils` 转换器）做 Entity ↔ DTO 转换，消除手写 getter/setter |
| P1-4 | 保持 JSON 字段名与旧 Entity 一致，保证前端零改动 |
| P1-5 | 补充 DTO 校验注解（`@NotBlank`/`@Size` 等），统一入参校验 |

**验收**：所有 Controller 签名改为 DTO/VO，`grep "Result<.*Entity>"` 返回 0，编译 + 全量接口回归通过。

---

### 阶段 2：Service 层重构（高风险，收益核心）
**目标**：Controller 不再直接注入 Mapper，业务逻辑 + 事务收敛到 Service。

| 项 | 内容 |
|---|---|
| P2-1 | 按域补齐 Service（`UserService` / `ProjectService` / `CaseService` / `ScenarioService` / `TaskService` / `ReportService` ...），每个 Service 持有自身 Mapper + 事务注解 `@Transactional` |
| P2-2 | Controller 改为只调 Service，瘦身为「参数校验 + 调 Service + 返回 VO」 |
| P2-3 | 复杂业务（用例版本快照、场景执行、报告汇总）从 Controller 下沉到 Service |
| P2-4 | 跨域调用走 Service 而非 Mapper（如 CaseService 需要 ApiDefinition 数据时注入 ApiDefinitionService） |
| P2-5 | 建立「Controller 禁止注入 Mapper」的架构约束（可配 ArchUnit 强制） |

**验收**：`grep "Mapper" controller/*.java` 返回 0；每个 Service 有对应单测；引入 ArchUnit 架构测试防止回退。

---

### 阶段 3：测试补齐（贯穿各阶段）
**目标**：关键链路有回归保障。

| 项 | 内容 |
|---|---|
| P3-1 | 后端：Service 层单测（Mock Mapper），覆盖核心业务（用例 CRUD、场景执行、报告生成、变量解析） |
| P3-2 | 后端：Controller 层 MockMvc 集成测试，覆盖认证、权限、错误码 |
| P3-3 | 前端：关键组件 + store 单测（Vitest + @vue/test-utils） |
| P3-4 | 引入 JaCoCo 覆盖率报告，设定覆盖率门槛（核心模块 ≥ 60%） |
| P3-5 | CI 集成（可选）：GitHub Actions 跑 `mvn test` + `npm test` |

**验收**：`mvn test` / `npm test` 全绿，覆盖率报告生成，核心 Service 覆盖率达标。

---

### 阶段 4：可观测性增强（低风险，锦上添花）
| 项 | 内容 |
|---|---|
| P4-1 | 接入日志 TraceId（MDC），全链路可追踪 |
| P4-2 | 慢 SQL 监控（MyBatis-Plus 拦截器 + 阈值告警） |
| P4-3 | 业务指标埋点（任务执行耗时、报告生成量、执行成功率） |
| P4-4 | 统一审计日志查询增强（可选） |

## 五、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Service 层重构改动大、易引入回归 | 业务功能破坏 | 先建基线测试（P3 前移），小步提交，ArchUnit 防回退 |
| DTO 字段名与 Entity 不一致 | 前端报错 | 严格保持 JSON 字段名一致，迁移前 diff 对比 |
| Flyway 引入后老库兼容 | 生产库迁移失败 | `baseline-on-migrate: true`，先在 localdev 验证 |
| MapStruct 增加构建复杂度 | 编译报错 | 用 Lombok + MapStruct 标准组合，annotationProcessor 配置好 |
| 监控端点暴露风险 | 安全 | `/actuator/**` 纳入认证，仅 health 公开 |
